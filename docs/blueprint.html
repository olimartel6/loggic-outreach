4
Sélection atomique du prochain lead
Cron */2 min
send-tick fire toutes les 2 min. Pour chaque mailbox active: vérifie limite quotidienne (5/jour défaut, éditable Settings), vérifie horaire (Lun-Ven 8h-17h défaut), puis appel claim_next_lead() qui fait SELECT ... FOR UPDATE SKIP LOCKED — race-safe, pas de double envoi même si 2 ticks lancent en parallèle.
send-tick (cron */2min) claim_next_lead RPC mailboxes.daily_limit campaigns.schedule
↓
5
Render + envoi SMTP
~3-8 min jitter / mailbox
Decrypt SMTP password via pgcrypto (clé dans private.app_secrets). Render {custom_subject} et {custom_body} avec les variables du lead. Threading: si étape 2+, ajoute headers In-Reply-To. Connexion SMTP TLS port 465 (Spacemail) → sendEmail(). Headers Gmail-friendly: List-Unsubscribe mailto (signal pas-bulk).
Spacemail SMTP 465 private.app_secrets (encryption_key) templates.ts render
↓
6
Logging + avancement du lead
Transactionnel
INSERT dans sends avec status=sent + Message-ID retourné par SMTP. UPDATE lead: current_step++, thread_message_id, last_subject, next_send_at = (delay du prochain step) + jitter aléatoire. Si plus d'étapes → status=completed. Unique index (lead_id, step_id) where status=sent bloque les doublons accidentels.
sends (audit trail) leads (current_step, next_send_at) jitter_next_for_mailbox RPC
↓
7
Détection des réponses + bounces
Cron */10 min
imap-poll fire toutes les 10 min. Pour chaque mailbox: connexion IMAP TLS, fetch messages depuis last_imap_uid_seen. Pour chaque nouveau message: extract In-Reply-To/References headers → match contre leads.thread_message_id (filtré par mailbox_id du lead pour éviter cross-campaign). Si match: status=replied. Si sender ressemble à mailer-daemon ou sujet contient "Delivery Status Notification" → status=bounced. Auto-stop séquence.
imap-poll (cron */10min) Spacemail IMAP 993 leads (status=replied/bounced) replies (audit)
Reliability
  • Atomic claim — FOR UPDATE SKIP LOCKED empêche double-envoi sur ticks concurrents
  • Retry exponentiel — 3 retries (5min → 15min → 60min) avant FAIL définitif
  • Unclaim sur erreur — lead libéré du mailbox errored, repris par autre mailbox active
  • Telegram alerts dedupliquées — crash, decrypt fail, FAIL final, mailbox status=error. Window 15 min same hash
  • Idempotent post-send — si SMTP succeeded mais DB crash, recovery via lastSend check
Sécurité
  • Encryption mailbox creds — pgcrypto AES sym, clé dans private.app_secrets
  • RLS partout — campaigns/leads readable par authenticated, sends/replies read-only via service_role
  • Whitelist auth — magic link, seulement 3 emails autorisés à créer un compte
  • Submission token — auth pour Hermes/UI sur /submit-leads, /build-demos, /submit-dm-drafts
  • Audit log — triggers sur campaigns/sequence_steps/mailboxes, RLS restreint à 1 admin
  • Rotation scripts — rotate-submission-token.py --yes, rotate-encryption-key.py (atomique)
Observabilité
  • /healthcheck — 200 si heartbeat <5min ET <50% mailboxes en error (pingable UptimeRobot, no JWT)
  • /daily-summary — cron 22h UTC, push Telegram: envoyés/réponses/bounces/failed/queue/mailboxes
  • audit_log table — qui a fait quoi quand sur les campagnes
  • sends + replies tables — historique complet pour analytics
  • Function logs Supabase — accessibles via Management API analytics endpoint
